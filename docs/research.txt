Yes. Given the way you are using the demo repositories—as dogfood, executable teaching material, and forcing functions for language design—I think demo-linear-algebra is not merely reasonable; it should probably be one of the highest-priority demo repos.

The current sw-MLPL description explicitly positions the language as array-oriented, functional-first, ML-focused, with native arrays/tensors, broadcasting, autograd, model facilities, and accelerator backends. The earlier ML milestone also specifically introduced dot, matmul, elementwise math, reductions, and logistic-regression training, while identifying rank/cell semantics as unfinished work. That makes linear algebra a particularly good place to stress exactly the abstractions sw-MLPL claims to specialize in.

I would organize the demo ecosystem around three axes

You already have what I would call programming-model demos:

demo-algorithms, demo-combinators, demo-functional-pipelines, demo-memory, demo-extensions, etc.

And you now have mathematical-structure demos:

demo-abstract-algebra and demo-category-theory.

What is missing is a third category:

computational mathematics that directly underpins ML

That category should get considerably more emphasis than pure mathematics because it directly supports your primary goal.

It could expose some important language gaps

This is where the repo becomes particularly valuable.

The current old ML milestone explicitly listed rank/cell semantics as future work. Linear algebra will put enormous pressure on precisely that area.

For example, what should this mean?

matmul(A, B)

when:

A : [batch, sequence, hidden]
B : [hidden, projected]

And what about:

A : [batch, heads, sequence, head_dim]
B : [batch, heads, head_dim, sequence]

You immediately encounter:

rank polymorphism
cells
broadcasting
named axes
batched matrix multiplication
axis permutation
shape errors
shape inference
higher-rank tensors
reductions over selected axes

Those aren't esoteric mathematical features. They are core ML programming-language semantics.

So demo-linear-algebra could become one of your primary tests of whether the APL/J/BQN influence is actually paying off.

One thing I would not do

I would resist implementing a giant MATLAB-like linear algebra library immediately.

For example, don't conclude:

"We need 75 new builtins."

Instead let the demos discover which things naturally decompose from existing sw-MLPL operations.

This is exactly analogous to your recent thinking about combinators and u:fns.

Linear algebra is an excellent laboratory for discovering those boundaries.

I would therefore not pursue "more mathematics" in the abstract.

demo-abstract-algebra and demo-category-theory then remain valuable orthogonal research/teaching experiments, rather than becoming the beginning of a project to recreate a university mathematics curriculum.

So my priority would be

Build demo-linear-algebra next.

Then let that repo identify shortcomings in:

rank/cell semantics
multidimensional array operations
named axes
batched operations
reductions
decomposition APIs

After that, demo-optimization and demo-probability-statistics would give you the three mathematical legs necessary to support almost everything from a simple regression model through transformers.

And I suspect demo-linear-algebra will be one of the strongest demos you have for explaining why sw-MLPL is an array-oriented language in the first place: the notation and execution model can potentially make vector → matrix → tensor → ML model feel like one continuous programming model instead of Python gluing together NumPy, framework tensors, object hierarchies, and helper libraries. That is very close to the core argument for the language.
